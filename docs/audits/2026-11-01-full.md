# Full audit, 1 November 2026

Scope: the repository, CI, the Vercel sandbox project and its domains, the Wizard sandbox, and production Salesforce (read only). Two independent line-by-line code reviews, one of the Apex engine and one of the web app and GitHub jobs. Nothing was changed in Wizard, Vercel, AWS or production. The two Wizard checks were read-only Apex scripts.

Commit audited: `main` at `7b521f9` (PR #19, 1 Nov 2026 15:35 UTC).

## Verdict

The sandbox build is real and works: every test passes, Wizard runs exactly what is on `main`, and the claim journey passed on all three demo campaigns at the last deploy (run 41320864260, on `f7c4f67`; not re-run for this audit, since only docs changed after it). It is **not ready for a production campaign**. The review found three faults that would let money go out wrongly (a flagged claim can be approved in one click, the claim deadlines are never enforced, a tier's spend ceiling is ignored), one confirmed way to run script on the page that takes bank details, and two exposure problems outside the code: the repository is public, and the production domain is serving the sandbox.

None of this changes the order of the roadmap. It adds one block of fixes in front of the first production campaign (roadmap phase 2, *Audit fixes*).

### Low

- A9: reminders take only the oldest 2,000 waiting claims and keep going after the deadline (`ClaimHubReminders.cls:300-321`).
- A10: a new invoice upload overwrites the old receipt and its read result, even on a complete claim.
- A11: one SOQL query per serial (up to 40 for 20 appliances), on top of legacy flows that have already hit 101 once.
- A12: the IP hash salt is the org Id, which isn't secret; every IPv4 address can be tried in minutes. Use an HMAC with a secret.
- A13: chat accepts "assistant" turns from the browser. Limited impact: no tools, one claim's data.
- A14, A15: a serial saved on another claim at the same moment during lodge is refused without a review flag; a malformed line from Claude stops an invoice upload with a 400.
- A16: CI goes green without testing Apex when the sandbox secrets are missing (`ci.yml:64, 82`).
- W9: upload type checked by declared type, not file bytes; staff PDF view under `CSP: sandbox` not tested in Chrome; designs can link to any https site; GitHub actions pinned to `@v4`, CLIs unpinned, no `permissions:` block on two workflows; a Salesforce outage shows claimants "not found"; page title hard-coded "Claim Hub (test)".
- I3: sandbox integration key still the original, exposed one (`SF_PRIVATE_KEY` unchanged since 30 Oct).
- I4: `BLOB_READ_WRITE_TOKEN` still stored readable (Vercel flags `readable-secret`), also set for Development; it had dropped off the roadmap. Project Node.js still 26.x.
- I5: one hub claim in Wizard (ENT-261031-211716, 31 Oct, AEG NZ) uses a `bamboomarketing.com.au` address, against rule 2. A staff address, not a customer's.
- I6: Wizard's `File_Base_URL__c` is still `trevor-claim-hub-test.vercel.app`, not a `test.entryform.claims` address.
- I7: `npm audit` reports 5 high advisories with one root, `zod` below 4.6.6 (memory exhaustion on oversized input, GHSA-mrhx-c7xc-m3w5), pulled in by `@vercel/blob` and `@vercel/oidc-aws-credentials-provider`. The app does not pass claimant input to it. Clear it when those packages update; Blob goes once old sandbox invoices expire.
- I8: no scheduled smoke test, though the runbook recommends one daily.
- I9: 21 old branches on GitHub; automatic deletion is off.
- I10: chat sessions carry a production Salesforce connector with write tools. "Production is read-only" is a rule, not a control. Consider a read-only integration for chats.
- I11: `electrolux-kitchen-refresh` in Wizard has no country, so the code treats it as AU without saying so. The builder should require the country.

## Test quality

- Apex: 71 test methods in `force-app` (79 with the 8 legacy-patch tests). Strong on the code count through the API, duplicate email, connection flag and percentage cap. Weak or missing: deadlines, spend bands, percentage rounding, the promotion-page chat limit, anything concurrent. `ClaimHubLogTest.errorsAndWarningsNeverThrow` passes with logging broken; `ClaimHubMonitorTest` asserts nothing after its run.
- Web: 45 cases, all on pure functions. Nothing tests the route handlers, `proxy.js`, cookie setting or the field allow-list. The CSS test misses the nested-tag bypass in W1.

## Checked and fine

Link codes are 256-bit random with exact, case-sensitive match; `Access_Token__c`, `Hub_Dedupe_Key__c` and `Hub_Serial_Key__c` are unique-indexed; the dispatcher's lock and re-check stop double sends; the trigger is bulk-safe; no SOQL injection; the console runs in user mode; claimant text is escaped in emails; file tickets are hashed, expire in 10 minutes and are checked against the claim's folder; the HTML side of the design clean-up held against every payload tried (event handlers, `javascript:` links, SVG, meta refresh, forms); the JWT sign-in, S3 key handling and field allow-list are sound; cookies are host-only, so they don't leak between brand subdomains; security headers are present. No secrets in any branch's history (all 78 commits scanned).
